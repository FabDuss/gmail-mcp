# WP-002 A send called while sending is off is refused before Gmail sees a request

## 2026-11-15T12:34Z · planner · ready

- Epic: EPIC-001 Send safeguards and revocation docs. Plan: PLAN-001 Send safeguards and revocation docs.
- Closes: NEED-005, NEED-006.
- Starts once WP-001 is `validated`.

### Slice

A client calls a tool, and the tool asks Gmail through the one method every Gmail request passes through, `api`. While sending is off, that method first asks the Gmail module whether the request path is sending, and refuses a sending request with an error that names `ALLOW_SEND`, before the session owner check, the rate limiter, any token refresh and any fetch. The client gets a tool result with `isError: true`, and Gmail and Google's token endpoint receive nothing. A draft still reaches Gmail, and with `ALLOW_SEND=true` the sending tools send as before.

### Needs

- NEED-005 Sending is refused while sending is off. Given a deployment with sending off, when any tool call would lead to sending, then the server refuses it and Gmail receives no request to send. This work-package closes it.
- NEED-006 Sending works when enabled. Given a deployment with `ALLOW_SEND=true`, when a client lists the tools, then the four sending tools are in the list, and a call to one of them sends. WP-001 brought the list; this work-package shows the send still goes through, and closes it.

#### The modules and what a caller may ask

- **The Gmail module.** Beside what it offers today, whether a request path is sending. It knows Gmail's methods and nothing of the deployment's settings. A path that does not parse is not sending, since `gmailFetch` could not send it either, so the function throws nothing.
- **The session agent, `GmailMCP`.** While sending is off, the method every Gmail request passes through refuses a request that is sending, before anything else it does. The refusal throws an error that says sending is off and names `ALLOW_SEND`; the SDK hands it to the client as a tool result with `isError: true` (FACT-011). With sending on, nothing changes on that path. Sending is on exactly when `ALLOW_SEND` is `true`, as `sendingIsOn()` decides.
- **The domain.** `CONTEXT.md`: sending is a request to Gmail that puts mail on the wire, a `POST` to `messages.send` or `drafts.send`. `messages.insert` is not sending. Sending off is `ALLOW_SEND` anything but exactly `true`, or unset.

#### Facts and decisions

- FACT-011: a handler that throws reaches the client as `{ content: [{ type: "text", text: <message> }], isError: true }`. In the handler tests' harness, which calls handlers directly, the error arrives as a rejected promise (FACT-018).
- FACT-013: `gmailFetch` is the only code that fetches Gmail and prefixes every path with `https://gmail.googleapis.com/gmail/v1/users/me`; its three calls sit in `GmailMCP.api`, which runs `assertSessionOwner`, `assertWithinRate`, `token()`, then `gmailFetch`, with a 401 retry after a forced refresh.
- FACT-014: `send_draft` posts to `/drafts/send`; `send_message`, `reply_all` and `forward_message` post to `/messages/send`.
- FACT-015: Gmail delivers mail through `users.messages.send` and `users.drafts.send` only; their upload variants live at the host root, which `gmailFetch`'s prefix cannot reach.
- FACT-016: dot segments resolve before a request leaves, percent escapes do not; `/drafts/abc/../send` resolves to `.../drafts/send`, `/messages/%73end` keeps its escape, and `/messages/../send` resolves to `/users/me/send`, no Gmail method. The query string is not part of the resolved path.
- FACT-018: the handler tests' harness, `makeAgent` and `boot`, with `ALLOW_SEND: "true"` in its `env`; after WP-001 it captures registrations in the `registerTool` form.
- DEC-001 Where the refusal of sending lives: in the Gmail request path, by the request, read at each use.

### What has no test, and why

- The "sending is off" wording beyond `ALLOW_SEND` is not pinned; the DoD asks only that the error names it.
- Malformed percent escapes (`/messages/%zz`) take the `catch` branch and answer false; no test, the DoD lists no such path.

### Choices the code does not make obvious

- `isSendingPath` compares the decoded resolved pathname with the base's own pathname plus `/messages/send` or `/drafts/send`, so the prefix is read from `BASE` and not repeated.
- Decoding happens after URL resolution, so `%2e%2e` segments, which URL treats as dot segments, resolve as fetch would, and `/messages/../send` stays not sending.
- The test helper turns sending off after registration by writing `env.ALLOW_SEND` on the harness agent, since the harness's `env` is a plain object read at each call.

### Gaps with the design

- None blocking. A doubled slash (`//messages/send`) is not judged sending, since fetch would send it to a different resolved path; I did not collapse slashes, because the brief says the path is resolved as `fetch` does.
