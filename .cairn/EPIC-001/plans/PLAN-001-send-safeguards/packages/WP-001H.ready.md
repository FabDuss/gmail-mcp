### Slice

A real SDK client, connected in process to the session agent, lists the tools and calls one. The code already registers each tool with its description, its input schema, and only `readOnlyHint` and `destructiveHint`, but no test reads those through the client, so three mutants of `GmailMCP.registerByKind` survived. This work-package adds tests that read them through the client and changes no behaviour. At the end, dropping a tool's description, its input schema, or adding a hint to a kind fails a test.

### Needs

None closed. The tests guard what WP-001 delivered for NEED-001 Read tools are marked read-only, NEED-002 Undoable writes are marked non-destructive and NEED-003 Destructive tools stay destructive, and TASK-001's DoD 8.

#### The modules and what a caller may ask

- **The session agent, `GmailMCP`.** A client lists each tool with the name, description and input schema it registered with. A read tool carries `readOnlyHint: true`; an undoable write `readOnlyHint: false` and `destructiveHint: false`; a destructive or sending tool `readOnlyHint: false` and `destructiveHint: true`. No tool carries `idempotentHint` or `openWorldHint` (DEC-002). `registerByKind` is the one registration method, and its interface stays as it is.
- **The domain.** `CONTEXT.md` names the kinds: read tool, undoable write, destructive tool, sending tool. Use those words in test names.

#### Facts and decisions

- FACT-010: `registerTool(name, config, cb)` hands the annotations to the client unchanged, and runs the same internal path as `tool()`.
- FACT-011: a handler that throws reaches the client as `{ content: [{ type: "text", text: <message> }], isError: true }`.
- FACT-018: the handler tests' harness, `makeAgent` and `start`; the SDK ships `InMemoryTransport` in `@modelcontextprotocol/sdk/inMemory.js`.
