# WP-001 A client lists every tool with the annotations of its kind, and the sending tools only while sending is on

## 2026-11-15T12:34Z · planner · ready

- Epic: EPIC-001 Send safeguards and revocation docs. Plan: PLAN-001 Send safeguards and revocation docs.
- Closes: NEED-001, NEED-002, NEED-003, NEED-004.
- Opening work-package of the plan, the core.

### Slice

A client connects to the session agent and lists its tools. Each of the 27 tools now registers through one registration method of the agent that takes its kind, and the SDK's `registerTool` hands the client the annotations of that kind. While sending is off, the four sending tools are left out of the list. One method of the agent decides whether sending is on, from `ALLOW_SEND` read without a cast from a declared `Env`. At the end, a real SDK client connected in process sees `readOnlyHint` and `destructiveHint` on each tool, and 23 or 27 tools depending on `ALLOW_SEND`.

### Needs

- NEED-001 Read tools are marked read-only. Given a client connected to the server, when it lists the tools, then each read tool carries `readOnlyHint: true`. This work-package closes it.
- NEED-002 Undoable writes are marked non-destructive. Given a client connected to the server, when it lists the tools, then each undoable write carries `readOnlyHint: false` and `destructiveHint: false`. This work-package closes it.
- NEED-003 Destructive tools stay destructive. Given a client connected to the server, when it lists the tools, then no destructive tool carries `readOnlyHint: true` or `destructiveHint: false`. This work-package closes it.
- NEED-004 Sending tools are absent while sending is off. Given a deployment with sending off, when a client lists the tools, then no sending tool is in the list. This work-package closes it.
- NEED-006 Sending works when enabled. Given a deployment with `ALLOW_SEND=true`, when a client lists the tools, then the four sending tools are in the list, and a call to one of them sends. This work-package brings the list half; WP-002 closes it.

### What to know

#### TASK-001 Every tool is listed with the annotations of its kind, and sending tools only while sending is on

Copied from `design.md`.

- **What changes.**
  - In the session agent, one registration method takes a tool's kind, name, description, input shape and handler. It registers the tool through the SDK's `registerTool`, with the annotations of its kind. While sending is off, it leaves sending tools out.
  - The kinds follow Q-004. Read tools are `whoami`, `search_messages`, `get_message`, `get_thread`, `list_labels`, `list_drafts` and `get_attachment`. Undoable writes are `modify_labels`, `modify_thread_labels`, `batch_modify_messages`, `create_draft`, `update_draft`, `untrash_message`, `untrash_thread`, `create_label`, `update_label`, `stage_attachment_begin`, `stage_attachment_append` and `stage_attachment_finish`. Destructive tools are `trash_message`, `trash_thread`, `delete_draft` and `delete_label`. Sending tools are `send_message`, `send_draft`, `reply_all` and `forward_message`.
  - One function of the deployment's settings decides whether sending is on: `ALLOW_SEND` is exactly `true`. TASK-002 reads the same function.
  - The set of sending tool names and the replacement of `server.tool` are removed.
  - The handler tests' harness captures registrations in the `registerTool` form.
  - The count check of CI counts registrations on the new registration call.
- **DoD.**

  2. In the same setup, each of the twelve undoable writes carries `readOnlyHint: false` and `destructiveHint: false`. Verified by a new test, as in line 1.

  5. With `ALLOW_SEND=true`, the list holds 27 tools, the four sending tools among them. Verified by extending the same existing tests, as in line 4.

#### The modules and what a caller may ask

- **The session agent, `GmailMCP`.** The client lists the tools and calls one. A read tool carries `readOnlyHint: true`; an undoable write `readOnlyHint: false` and `destructiveHint: false`; a destructive tool `readOnlyHint: false` and `destructiveHint: true`, written out although it is the protocol's default (FACT-007), so that a client reading only what is present sees it. A sending tool carries the annotations of a destructive tool. `idempotentHint` and `openWorldHint` stay unset (DEC-002). Sending is on exactly when `ALLOW_SEND` is `true`; `ALLOW_SEND=TRUE` or `ALLOW_SEND=1` is sending off.
- **The deployment's settings.** `ALLOW_SEND` is a secret like the four that setup puts, typed `string` in `Env` (DEC-003). Edit `worker-configuration.d.ts` by hand: regenerating it would change its header hash and other lines, which TASK-003 DoD 1 forbids.
- **The count check of CI.** It counts every registration in the source, the four sending tools included, so 27 whatever the setting (DEC-004). Its pattern must match the calls of the new registration method in `init`, and not the method's own declaration or the `registerTool` call inside its body.
- **The domain.** `CONTEXT.md` names the kinds: read tool, undoable write, destructive tool, sending tool, and sending off. Use those words, and none of their `_Avoid_` lines.

#### Facts and decisions

- FACT-007: an unannotated tool counts as destructive (`destructiveHint` defaults to true).
- FACT-010: `registerTool(name, config, cb)` runs the same internal path as `tool()`, accepts the same Zod 4 shapes, gives an empty shape's callback `(args, extra)`, and hands the annotations to the client unchanged.
- FACT-012: the agent framework awaits `init()` and never touches registration.
- FACT-017: `wrangler types` types each key of `.dev.vars` as a required `string`, and the committed `worker-configuration.d.ts` types the four secrets of `.dev.vars.example` that way; a deploy never deletes a secret.
- FACT-018: the handler tests' `makeAgent` stubs `server` with only `tool(name, description, shape, cb)` and sets `ALLOW_SEND: "true"`; the describe block "sending is off unless the deployment enables it" counts 23 and 27 handlers. The SDK ships `InMemoryTransport` in `@modelcontextprotocol/sdk/inMemory.js`.
- FACT-019: `scripts/check-counts.py` matches `badge/tools-(\d+)-` in the three READMEs, against its count of registrations in `src/index.ts`.
- FACT-004: the count check's line about the test count already fails, 253 claimed against 255 run. This is a known red; do not touch the test count claims.
- FACT-020: the sketch's registration method infers each handler's argument types from its `inputSchema`, and rejects a handler that misreads them.
- FACT-021: `noUnusedLocals` and `noUnusedParameters` are on, which is why the sketch's methods are `protected` and their parameters start with `_`.
