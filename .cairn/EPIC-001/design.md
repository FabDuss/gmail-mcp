# EPIC-001 Send safeguards and revocation docs: design

The design is short because the epic changes two places in one module, the registration of the tools and the path every Gmail request takes, plus documentation.

## Domain

`CONTEXT.md` is new. It carries the concepts the pilot confirmed in the intent, Q-004 and Q-007. No term changes meaning, so no wait went to the pilot.

- **Read tool.** `get_message` returns a message and changes nothing, so it is a read tool. `whoami` reads the profile and is one too. `list_drafts` lists drafts without writing one, so it stays a read tool even though drafts are written elsewhere.
- **Undoable write.** `modify_labels` adds a label that a second call removes. `untrash_message` takes a message out of the trash, and `trash_message` puts it back. `stage_attachment_begin` writes only to the session's own storage, which a staging's expiry clears.
- **Destructive tool.** `delete_label` removes a label that no tool brings back. `trash_message` is destructive by the pilot's choice in Q-004, even though `untrash_message` reverses it. `send_message` is destructive because a sent message cannot be recalled.
- **Sending tool.** `reply_all` sends at once, so it is a sending tool. `create_draft` with `replyToMessageId` builds the same reply and holds it as a draft, so it is an undoable write. `send_draft` sends a draft that already exists, so it is a sending tool.
- **Sending.** A `POST` to Gmail's `messages.send` or `drafts.send` is sending (FACT-015). `messages.insert` puts a message in the user's own mailbox and is not sending. A send-as verification mail is not sending for this server, because Gmail restricts that method to domain-wide delegation, which a user's grant never has.
- **Sending off.** `ALLOW_SEND` unset is sending off. `ALLOW_SEND=TRUE` or `ALLOW_SEND=1` is sending off too, because only the exact value `true` turns sending on. `ALLOW_SEND=true` is sending on.
- **Revocation path.** Narrowing `ALLOWED_EMAILS` is a revocation path for new sign-ins. Revoking at myaccount.google.com/connections is a revocation path for every grant of that account. Rotating the Google client secret is not one (FACT-006).

## Modules

### The session agent, `GmailMCP` (modified)

- **Responsibility.** Serves one MCP session for one Google account: registers the tools and runs each call against Gmail.
- **What a caller may ask.** The client lists the tools and calls one. The list gives each tool its annotations, which follow from its kind: a read tool carries `readOnlyHint: true`, an undoable write `readOnlyHint: false` and `destructiveHint: false`, a destructive tool `readOnlyHint: false` and `destructiveHint: true`. A sending tool carries the annotations of a destructive tool.
- **Rules.** One registration method of the agent takes each tool's kind with its name, description, input shape and handler, and registers it through the SDK's `registerTool`. While sending is off, that method leaves sending tools out. While sending is off, the method every Gmail request passes through refuses a request that is sending, before anything else it does. Sending is on exactly when the deployment's `ALLOW_SEND` is `true`. One function of the deployment's settings decides it, and both the registration method and the Gmail request path read it at each use.
- **Errors.** A refused sending request throws an error that says sending is off and names `ALLOW_SEND`. The SDK hands it to the client as a tool result with `isError: true` (FACT-011).
- **Exemplar module.** The agent's own current form: private methods such as `assertWithinRate` and `api`, each with a comment that says why, and the tool registrations of its `init`. Its tests follow the handler tests and their harness.

### The Gmail module (modified)

- **Responsibility.** Gmail's wire format and its HTTP call, as pure functions and `gmailFetch`.
- **What a caller may ask.** Beside what it offers today, whether a request path is sending: it resolves the path against Gmail's base URL as `fetch` does, decodes its percent escapes, and answers whether the result names `messages.send` or `drafts.send`.
- **Rules.** It knows Gmail's methods and nothing of the deployment's settings.
- **Errors.** None. A path that does not parse is not sending, since `gmailFetch` could not send it either.
- **Exemplar module.** Its exported pure helpers such as `normalizeMessageId`, with their unit tests in the Gmail tests.

### The deployment's settings (modified)

- **Responsibility.** The `Env` type generated by `wrangler types`, and the example of local settings.
- **Rules.** `ALLOW_SEND` is a secret like the four that setup puts, typed `string` in `Env`. The wrangler config declares no `ALLOW_SEND` var (DEC-003).
- **Exemplar module.** The four secrets as `Env` and the example of local settings declare them today.

### The count check of CI (modified)

- **Responsibility.** Fails when a README badge states a tool count other than the number of tool registrations in the source, or when a README claims a test count other than the number of tests the suite runs. With its fix option, it rewrites the claims it reads instead (FACT-027).
- **Rules.** It counts every registration in the source, the four sending tools included, so 27 whatever the setting (DEC-004). TASK-006 changes none of its rules.
- **Exemplar module.** Its own current form.

### The documentation (modified)

- **Responsibility.** The English README, its Japanese and Chinese translations, and the landing page. The three READMEs state the tool count and the test count that the count check reads.
- **Exemplar module.** The "Who can sign in" section, which documents `ALLOWED_EMAILS`, is the model for the `ALLOW_SEND` section.

## Core and risks

The epic stands on two results: a client sees each tool's kind in the list, and no sending request reaches Gmail while sending is off. TASK-001 and TASK-002 carry them. The most uncertain point is the typing of the registration method: it must pass each tool's input shape through to the SDK's generic `registerTool` so that every handler keeps its typed arguments. The type check finds a miss, and the cost is a rework of one method's signature.

TASK-006, added after the closing review of PLAN-001, holds only if no test enters the suite after it lands, since every new test moves the count it states.

## Decisions

### DEC-001 Where the refusal of sending lives

- **Candidates.**
  - A. Registration only, by a set of tool names, as today (FACT-002).
  - B. A check at the start of each sending tool's handler.
  - C. The Gmail request path refuses any request that is sending while sending is off, and registration leaves sending tools out by their kind. Both read the same decision.
- **Choice.** C. Every Gmail request passes through one method of the session agent (FACT-013), so a refusal there holds for every tool, including a tool added later under the wrong kind or a name missing from a set. The request decides, not the tool: Gmail delivers mail through exactly two methods (FACT-015), which the Gmail module recognises after the path resolves as `fetch` resolves it (FACT-016). The decision is read at each use rather than kept from start-up, so the request path never disagrees with the settings.
- **Rejected.** A lets a sending tool absent from the set, or registered another way, send (FACT-002), which is the hole Q-007 closes. B repeats the check in four places and misses any fifth tool that sends.
- **ADR.** None. The choice is local to one module and cheap to change.

### DEC-002 Registration through registerTool, by kind

- **Candidates.**
  - A. Keep the deprecated `tool()` overloads and pass the annotations positionally, keeping the replacement of `server.tool`.
  - B. Call `registerTool` at each of the 27 sites with a literal annotations object, and gate the sending tools by a name set.
  - C. One registration method of the session agent takes the tool's kind and calls `registerTool` with the annotations of that kind.
- **Choice.** C. The kind is a required argument, so no tool registers without saying what it is, and the annotations and the gating follow from it in one place. `registerTool` runs the same internal path as `tool()`, accepts the same Zod 4 shapes, and hands the annotations to the client unchanged (FACT-010). The agent framework does not touch registration (FACT-012). A destructive tool carries `destructiveHint: true` written out, although it is the protocol's default (FACT-007), so a client that reads only what is present sees it. `idempotentHint` and `openWorldHint` stay unset: the intent asks for neither.
- **Rejected.** A keeps an API the SDK marks deprecated and keeps the replacement of `server.tool`, which only gates calls that go through that one method. B writes 27 annotation objects by hand and keeps the name set that DEC-001 drops.

### DEC-003 How ALLOW_SEND is declared

- **Candidates.**
  - A. A var in the wrangler config with the value `false`.
  - B. A secret like the other four: listed in the example of local settings, typed `string` in the generated `Env`, and set by the operator with `wrangler secret put ALLOW_SEND`.
  - C. An optional member added to `Env` by declaration merging in the source.
- **Choice.** B. It follows the four secrets setup already puts (FACT-017). A deploy never deletes a secret, so an operator who turns sending on keeps it on across deploys. The comparison with `"true"` handles the unset case at run time, as the four secrets are handled today.
- **Rejected.** A types the var as the literal `"false"`, so the comparison with `"true"` stops type-checking. A deploy would also replace an operator's `ALLOW_SEND` secret with the var after one confirmation (FACT-017), and setup copies the config only once, so the var would not reach a deployment set up earlier. C clashes with a regenerated `Env` the day a developer's local settings hold the key, because the generated member is required.
- **Out of the epic.** The Deploy to Cloudflare button keeps asking for the four secrets it asks for today. Sending off is the default, and the intent does not ask the button to change.

### DEC-004 The count check counts every registration

- **Candidates.**
  - A. Count every registration in the source, on the new registration call.
  - B. Count only the tools registered with sending off, 23.
- **Choice.** A. The pilot kept the badge at 27 and a sentence for the gated four (Q-006). The check stays a text count of the source, as today (FACT-009).
- **Rejected.** B contradicts Q-006, which rejected advertising 23.

## Impact

### What changes

- All 27 tools register through `registerTool` and carry annotations. A client that reads annotations now shows read tools and undoable writes as safe, and keeps asking before a destructive tool. Every tool keeps its name, description and input schema.
- The path every Gmail request takes gains a refusal that throws before the session owner check, the rate limiter and any token refresh. With sending on, nothing changes on that path.
- The handler tests' harness stops working the moment registration changes, because its stub has only `tool()` (FACT-018).
- The count check's pattern stops matching the source the moment registration changes (FACT-009).
- The nine test-count claims of the three READMEs, the badges and the sentences of their testing sections, move from 253 to the number the suite runs, 275 at 6ee2fd3 (FACT-027). The CI step "Tool and test counts match the source" turns green, and the known red of the epic's baseline on those claims no longer holds.

### The facts it is safe because of

- **FACT-013**, pointed: every Gmail request goes through one method of the session agent, and `gmailFetch` prefixes every path with Gmail's base URL. A refusal at the top of that method therefore stops every sending request, and no upload variant of a send method is reachable.
- **FACT-010**, ran: the throwaway script registered tools through `registerTool` with annotations and listed them through a real SDK client. Each tool came back with its annotations exactly as given, and a handler that threw came back as `isError: true` (FACT-011).
- **FACT-016**, ran under bun: a dot segment resolves before the request leaves, so the predicate must judge the resolved path, and does.
- **FACT-027**, ran: the count check's fix, run on copies of the three READMEs, changed exactly the nine claims and only their number, and the check then passed on tools and tests. A fix through the check therefore cannot rewrite a year, an RFC number or a port elsewhere in the READMEs.

### Risks

- **The count check fails CI.** It counts `this.server.tool(` and would find none after the change. The chance is certain without a fix, and the cost is a red CI step. The check is to run it and read that no line about tools fails. That is the cheapest check before integration, and it is a DoD line of TASK-001.
- **The count check already fails on the test count.** The README claims 253 tests while the suite runs 255 (FACT-004), and the pilot first left that out of the epic. Each work-package that adds tests widens the gap. The DoD lines of TASK-001 and TASK-005 read only the tool line of the check. Since the closing review of PLAN-001, TASK-006 closes the gap (NEED-009).
- **A test lands after TASK-006.** Any test that enters the suite after the claims are rewritten moves the count, and the step turns red again. The chance is low: TASK-006 is the epic's last TASK, and `origin/main` holds no commit absent from the epic (FACT-027), so the merge of main at the last barrier adds no test today. The cost is one more run of the check's fix. The check is the barrier's run of the count check, on the epic head that the PR carries.
- **Handler arguments lose their types.** A registration method that does not pass the input shape through as a generic leaves handler arguments untyped. The chance is medium, and the cost is a compile error or untyped handlers. The type check of the gates finds it.
- **Every handler test breaks with the harness.** Its stub has no `registerTool` (FACT-018). The chance is certain, and the fix belongs to TASK-001.

### Cleared

- **Settings methods that mail a verification message.** Gmail restricts them to domain-wide delegation, and the code calls only `GET /settings/sendAs` (FACT-015, FACT-013).
- **An id that turns a path into a send path.** Ids pass through `encodeURIComponent`, so they cannot carry `/` or a raw `%`. A `..` id resolves before the request leaves, and the predicate judges the resolved path (FACT-016). `/messages/../send` resolves to `/users/me/send`, which is no Gmail method.
- **The agent framework replacing registration.** It does not (FACT-012).
- **An unset ALLOW_SEND typed as `string`.** The four secrets already work this way, and the comparison with `"true"` is false for `undefined`.
- **The plugin manifest's list of 27 tools.** It does not drive the server's list, and nothing in CI reads it (FACT-019). It stays as it is.
- **The 401 retry and the 429 backoff.** Both run after the refusal, so a refused request never reaches them.
- **A test-count claim the check does not read.** The landing page states no test count, and every claim in the three READMEs matches a pattern of the check (FACT-027).

### The cheapest check before integration

Run the count check after the registration change and read that it prints no failing line about tools. It is DoD line 7 of TASK-001. For TASK-006, run the count check and read that it exits 0, which is its DoD line 1.
